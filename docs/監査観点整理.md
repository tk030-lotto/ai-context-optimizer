# 監査観点整理

この資料は、監査パックや設計資料だけを起点に、どこまで判断できるかを整理したものです。
監査時の見立てを先に作り、必要な箇所だけコード確認するための下敷きとして使います。

## 資料だけで出せるもの

- 仕様の抜け
- 設計上のリスク
- 変更漏れの候補
- 監査観点の優先順位
- 壊れやすそうな箇所の推定

## 資料だけでは断定しにくいもの

- 実際に再現するバグ
- その行が原因だと断言できる修正点
- 境界条件での不具合
- 実装と仕様のズレの最終確認

## 結論

- バグ及び修正点を確定するには、少なくとも該当箇所のコード確認が必要
- ただし、毎回すべてのコードを見る必要はない
- ふつうは、資料から怪しい箇所を絞り、その周辺だけ確認すれば十分

## 実務フロー

1. 資料だけで候補を出す
2. 怪しいファイルや関数を絞る
3. その周辺コードだけ確認する
4. 修正点を確定する

## 資料だけから出せる監査項目

- 仕様と実装の対象範囲が一致しているか
- 画面や出力フォーマットの説明が十分か
- エラーハンドリング方針が明記されているか
- ローカル完結やネットワーク禁止の方針が守られているか
- 変更対象のフェーズと優先順位が明確か

## ソース確認が必要な監査項目

- 条件分岐の実装漏れ
- パースや解析の取りこぼし
- 依存解決や参照先解決の誤り
- 境界値での誤動作
- 実装と仕様書の一致確認

## 使い方

- まずこの資料を読んで、監査の焦点を決める
- 次に監査パックや仕様書で対象を絞る
- 最後に該当コードだけ確認して、修正の確度を上げる
